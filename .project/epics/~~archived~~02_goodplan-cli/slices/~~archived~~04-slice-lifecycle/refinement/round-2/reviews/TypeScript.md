**[IMPORTANT]** Phase 2 COMPLETE_SLICE handler has no mechanism to communicate `deferredSkipped`/`learningsRolledUp` counts to the RPC layer
Phase 2 task 4 step 2 says "The RPC layer should include a `deferredSkipped` count in the result so callers know items were dropped" and step 8 says "learningsRolledUp: count how many learnings were rolled up to epic and project levels." But the state machine returns `ProjectState | StateError` -- there is no sideband channel for these counts. The `epicComplete` detection was correctly moved to the RPC layer (step 7), but `deferredSkipped` and `learningsRolledUp` were not given the same treatment. The RPC layer's `buildCompleteResult` would need to independently derive these counts by diffing old vs new state (e.g., counting new entries in target slice deferred arrays and in epic/project learnings.jsonl). Phase 2 should either: (a) explicitly state that these counts are derived by the RPC layer via state diffing (matching epicComplete), or (b) remove the counts from the state machine phase and place them entirely in Phase 3's `buildCompleteResult` task. Currently the responsibility is split ambiguously.
Resolution: DIRECTLY_ACTIONABLE

**[IMPORTANT]** Phase 2 `slice-complete.ts` learnings rollup writes to JSONL files that may not exist yet
Phase 2 task 4 step 3 says "write `event.learnings` to `slices/<name>/learnings.jsonl`" and "append to `epics/<epic>/learnings.jsonl`" and "append to top-level `learnings.jsonl`". The state machine uses `getJsonl()` to read existing entries before appending. With `noUncheckedIndexedAccess: true`, `getJsonl()` returns `T[] | undefined` for non-existent files. The existing pattern in `appendActivityLog` (helpers.ts line 118) handles this with `?? []`. The plan should explicitly note that each JSONL write in COMPLETE_SLICE must handle the `undefined` case (file doesn't exist yet) with `?? []`, since slice-level and epic-level learnings.jsonl files won't exist until the first completion. This is not a bug per se, but given the handler's complexity (5+ JSONL writes), explicitly noting this pattern prevents a subtle runtime crash.
Resolution: DIRECTLY_ACTIONABLE

**[MINOR]** Phase 3 `BeginPayloadMap` change makes `goal` required for all `create` calls including project
Phase 3 task 3 changes `create` from `{ name: string; goal?: string }` to `{ name: string; goal: string; epic?: string }`. This makes `goal` required for all `create` calls, but `INIT_PROJECT` (project creation via `begin('create', {type:'project'}, ...)`) uses `name` only -- `goal` is not part of the project entity. The existing `buildCreateEvent` for `target.type === 'project'` (begin.ts line 117) only reads `payload.name`. Making `goal` required forces project creation callers to pass a dummy goal string. The current codebase has `goal?: string` (optional) which works for both project and epic creation. The plan should keep `goal` optional OR use a discriminated payload approach (e.g., `create: { name: string } & ({ goal: string; epic?: string } | { goal?: never; epic?: never })`), though the latter adds complexity. Simplest fix: keep `goal` as `goal?: string` and add runtime validation in `buildCreateEvent` for slice/epic targets (matching the existing pattern for epic where goal is runtime-checked at begin.ts line 119).
Resolution: DIRECTLY_ACTIONABLE

**[MINOR]** Phase 1 `learningInputSchema` field list does not match `learningEntrySchema`
Phase 1 task 2(a) says `learningInputSchema` "includes category enum, summary, detail, tags, rollupTo array but omits `source` and `rollup` fields". Looking at the existing `learningEntrySchema` (src/schemas/records/learning.ts), its fields are: `category`, `summary`, `detail`, `tags`, `source`, `rollup`, `rollupTo`. Omitting `source` (injected by RPC) is correct. But omitting `rollup` (a boolean) while keeping `rollupTo` (an array) is semantically odd -- `rollup` appears to be a derived/redundant field (true when `rollupTo.length > 0`). The plan should clarify: is `rollup` computed from `rollupTo` in the RPC layer, or should the input schema include it? If computed, add a note in Phase 3 that the RPC layer sets `rollup: learning.rollupTo.length > 0` when constructing the full `LearningEntry`.
Resolution: DIRECTLY_ACTIONABLE

**[MINOR]** Phase 4 `slice:create` command calls `begin()` with inconsistent argument style
Phase 4 task 1 says the command "Calls `begin('create', {type:'slice', name}, {name, goal, epic})`". But `begin()` signature is `begin(projectDir, phase, target, payload)` -- the first positional arg is `projectDir`, not `phase`. The existing `epicCreateCommand` (src/commands/epic/create.ts line 32) calls `begin(projectDir, "create", { type: "epic", name: input.name }, { name: input.name, goal: input.goal })`. The plan's pseudo-code omits `projectDir` and uses shorthand. This is a documentation clarity issue, not a code issue, but could confuse implementers. The plan should use the full 4-argument form matching existing commands: `begin(projectDir, 'create', {type:'slice', name: input.name}, {name: input.name, goal: input.goal, epic: input.epic})`.
Resolution: DIRECTLY_ACTIONABLE

**[MINOR]** Phase 2 `setSliceStatus` helper signature differs from `setEpicStatus` without explanation
Phase 2 task 7 lists helpers including `setSliceStatus(state, name, slice, newStatus, ts)` which takes the full Slice object. The epic helpers already have this dual pattern -- just note it's deliberate.
