# Software Architecture Review: Tracer Bullet Plan

## Issues

**[IMPORTANT] Directory structure diverges from conventions.md and architecture _overview.md**
The plan (Phase 1) creates `src/core/data/`, `src/core/state/`, `src/core/context/` which aligns with the architecture overview. However, the project `conventions.md` lists a different structure: `src/core/state/`, `src/core/data/`, `src/core/context/`, `src/core/workflow/` (not `src/core/rpc/`). The plan creates no `src/core/workflow/` directory. More importantly, the plan puts commands in `src/commands/global/` (Phase 4: `src/commands/global/init.ts`, Phase 5: `src/commands/global/status.ts`), but conventions.md shows `src/commands/epic/`, `src/commands/build/`, `src/commands/resource/`, `src/commands/global/` while the architecture conventions.md says commands are organized by namespace: `epic/`, `slice/`, `quest/`, `decision/`, `learning/`, `activity/`, `global/`. The plan's choice of `src/commands/global/` for init and status is correct per the architecture docs (these are global commands), but the plan should not create placeholder directories for namespaces not yet needed in this slice -- that is fine. The real issue: `conventions.md` lists `src/commands/build/` and `src/commands/resource/` which don't appear in the architecture docs at all. This is a documentation inconsistency the plan should not perpetuate. The plan should follow the architecture docs (which are more detailed and authoritative) and create only `src/commands/global/` for this slice.
Resolution: DIRECTLY_ACTIONABLE

**[IMPORTANT] Plan bypasses runMain for custom exit codes but doesn't explain how**
The citty research (citty.md) explicitly documents that `runMain` exits with code 1 for all errors -- there is no exit code differentiation. The plan (Phase 3) requires exit code 2 for validation/unknown command errors and exit code 3 for state errors (Phase 4: STATE_ALREADY_INITIALIZED). The research notes "Custom error handling requires wrapping `runCommand` instead of using `runMain`" but the plan's Phase 3 tasks say "Wire `src/index.ts` to import and run the main command" and "Handle unknown commands: catch citty's unknown command error, return exit 2". The plan does not specify whether to use `runMain` or `runCommand` -- this is a critical implementation detail that determines the entire error handling architecture. Using `runMain` means fighting citty's built-in exit(1) behavior; using `runCommand` means building your own top-level error handler and help dispatcher. The plan should explicitly specify: use `runCommand` (not `runMain`) as the entrypoint, implement a custom top-level runner that catches errors and maps them to the correct exit codes (1/2/3), and handles `--help` rendering.
Resolution: DIRECTLY_ACTIONABLE

**[IMPORTANT] readJson/writeJson naming diverges from architecture's readEntity/writeEntity**
Phase 2 creates `src/core/data/json.ts` with `readJson(path, schema)` and `writeJson(path, data, schema)`, and `src/core/data/project.ts` with `readProject()`/`writeProject()`. The Data Layer API architecture doc specifies `readEntity<T>(path, schema)` and `writeEntity<T>(path, data, schema, expected?)`. While this is a tracer bullet and only project.json is in scope, the function naming sets a precedent. Starting with `readJson`/`writeJson` means a rename to `readEntity`/`writeEntity` in slice 02, or maintaining two naming conventions. The plan should use `readEntity`/`writeEntity` from the start (even if the implementation is minimal) to avoid unnecessary churn. The `project.ts` wrapper is fine as a convenience layer.
Resolution: DIRECTLY_ACTIONABLE

**[IMPORTANT] StatusResult schema location and shape need alignment with commands-api**
Phase 2 creates `src/schemas/commands/status.ts` with a StatusResult schema. The commands-api.md defines `status` as a global command that returns project state including active pointers. However, Phase 5's Expected Behavior shows the StatusResult containing `activeEpic`, `activeSlice`, `activeQuest` as top-level nullable objects -- but the architecture's `project.json` data model stores these as string names (not objects). The plan says "nullable objects with name, status, phase" for the active pointers in StatusResult, which means the status command must join data from project.json (which has the name) with the entity JSON files (which have status and phase). For this tracer bullet, the entity files don't exist yet (only project.json is initialized). The plan should clarify: active pointers in StatusResult are null for a fresh project (which it does in Phase 5), but the schema definition in Phase 2 should explicitly document that the "objects with name, status, phase" shape is a projection that requires entity lookup -- and in this slice, null is the only valid value since we never create epics/slices/quests. This isn't a bug but the schema should be defined knowing it will only ever be null in this slice's scope.
Resolution: DIRECTLY_ACTIONABLE

**[MINOR] stdin infrastructure (Phase 3) is dead code in this slice**
Phase 3 creates `src/util/stdin.ts` with TTY detection, JSON parsing, 1 MB size limit, and `src/util/validate.ts` with merge logic. Neither `init` nor `status` commands accept stdin input -- init uses only `--name` flag, status uses only `--json` and `--smoke-jq`. The stdin infrastructure has zero callers and zero tests in this slice. Including it is defensible (shared by all future mutation commands, reduces slice 02 scope), but it should be explicitly tested in Phase 3 even without command-level callers -- add unit tests for stdin.ts and validate.ts in Phase 3's tasks. Currently Phase 3's verification only checks `--help` and `badcommand` behavior; the stdin module is untested.
Resolution: DIRECTLY_ACTIONABLE

**[MINOR] --smoke-jq flag name uses hyphen prefix inconsistently with global flags**
The plan introduces `--smoke-jq` as a temporary flag on the status command. The architecture's global flags use `--json`, `--quiet`, `--query`, `--verbose`, `--inline` -- all single words. Command-specific flags in the architecture use `--name`, `--epic`, `--slice`, `--reason`, `--override`, `--index`. The `--smoke-jq` flag is the only hyphenated flag name in the entire plan. This is minor since it's temporary (removed in slice 05), but for consistency it could be `--smokejq` or just `--jq-smoke`. More importantly, the plan should note that this flag is command-specific to status (not a global flag) and should NOT be added to the global args spread.
Resolution: DIRECTLY_ACTIONABLE

**[MINOR] Phase 1 directory structure includes src/core/state/ and src/core/context/ which are empty through all 6 phases**
The plan creates `src/core/state/` and `src/core/context/` in Phase 1 but never populates them. These directories exist only as placeholders for future slices. This is harmless but Biome's lint pass may need configuration to ignore empty directories, and the Expected Behavior check `ls src/commands/ src/core/ src/schemas/ src/util/` verifies directories exist but doesn't distinguish empty from populated. Consider either: (a) not creating these directories until they're needed, or (b) adding a brief comment in Phase 1 tasks noting these are scaffolding for future slices.
Resolution: DIRECTLY_ACTIONABLE

## Score: 7/10

The plan demonstrates solid bottom-up layering and clear phase boundaries. The Expected Behavior sections with before/after checks are excellent -- they give implementors concrete verification at each step. However, there are several architectural alignment issues: function naming that diverges from the architecture spec (`readJson` vs `readEntity`), unresolved citty entrypoint strategy (runMain vs runCommand) that fundamentally shapes the error handling architecture, and dead stdin code that goes untested. None of these are blocking, but together they create unnecessary tech debt that slice 02 will inherit. Fixing the naming alignment, specifying the citty entrypoint approach, and adding stdin unit tests would bring this to 9+.
