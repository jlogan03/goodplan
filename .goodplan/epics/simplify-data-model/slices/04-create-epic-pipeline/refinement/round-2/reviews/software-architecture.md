# Software Architecture Review — Create-Epic Pipeline Plan (Round 2)

## Issues

**[IMPORTANT] Refinement loop uses `submit-refinement` but the CLI command is `submit-refine-architecture` / `submit-refine-slices` with different response semantics**
Phase 4 step 6 says: `gp submit-refine-architecture --epic <name> --json` with `{"scores": {...}, "round": N}`. Two problems: (1) The `SubmitResult` returned by `submit-refine-architecture` uses `advanced: boolean` to indicate whether scores met the threshold (i.e., whether the status changed from `refining-architecture` to `architecture-refined`). The plan says "Check exit: all scores >= 9 AND no CRITICAL/IMPORTANT issues" — but this duplicates logic that belongs to the CLI's state machine. The orchestrator should submit scores, then check the `advanced` field on the response to determine whether to exit the loop, exactly as the transition table specifies (`scores below threshold AND !override` stays in `refining-architecture`; `scores meet threshold OR override` advances to `architecture-refined`). (2) The plan says `{"scores": {...}, "round": N}` but `submitRefineArchitectureInputSchema` expects `{"scores": {...}}` — `round` is not a stdin field (the CLI tracks rounds internally). The plan-slice orchestrator (line 345) correctly uses only `{"scores":{...}}`. The same issue applies to `submit-refine-slices` in Phase 6.
Resolution: DIRECTLY_ACTIONABLE

**[IMPORTANT] Refinement loop specifies coordinator+synthesis agents but plan-slice uses a simpler, proven pattern**
Phase 4's refinement loop specifies 4 agent types per round: refinement-coordinator (step 1), reviewers in parallel (step 2), synthesis (step 3), then editor (step 5). However, the plan-slice orchestrator — the proven pattern this plan claims to follow — uses a slightly different flow: coordinator selects reviewers, orchestrator spawns reviewers, orchestrator writes reviewer output to disk (step 4f-iii), then spawns synthesis to merge, then evaluates exit conditions using per-reviewer scores from reviewer returns (not synthesis scores), then spawns editor. The create-epic plan says "Check exit: all scores >= 9 AND no CRITICAL/IMPORTANT issues" at step 4, but doesn't specify where those scores come from — the synthesis agent? Per-reviewer returns? The plan-slice pattern is clear: per-reviewer scores from individual reviewer returns drive the exit decision. The plan should explicitly state it follows the plan-slice refinement loop pattern (steps 4f-i through 4f-vi) rather than re-specifying a slightly different variant.
Resolution: DIRECTLY_ACTIONABLE

**[IMPORTANT] Phase 4 architecture file copying should use CLI `paths.architecture` from submit response, not manual copy**
Round 1 flagged this (I2) and the plan now mentions using CLI response paths. However, the plan still says "Submit architecture: `gp submit-architecture --epic <name> --json` — pass temp dir file paths" and separately "Use the CLI response's path fields." The mechanics are unclear: `submit-architecture` is a state transition trigger that expects content already on disk (verified in `submit.ts` line 5: "Content is already on the filesystem"). The architecture-phase agent writes to a temp dir, but `submit-architecture` expects files at the CLI-managed location. The correct flow is: (1) query `paths.architecture` from `gp epic:define-architecture` response (the begin command), (2) pass that path to the architecture-phase agent as the write destination, (3) agent writes directly to the CLI-managed path, (4) `submit-architecture` triggers the state transition. This matches how plan-slice works — the agent writes to the CLI-managed path, not a temp dir. Alternatively, use `start-architecture` which returns the target paths in the context bundle.
Resolution: DIRECTLY_ACTIONABLE

**[MINOR] `start-refine-architecture` / `start-refine-slices` context bundles not used for refinement loops**
The plan's refinement loops manually assemble paths for coordinator, reviewer, and editor agents. The CLI provides `gp start-refine-architecture --epic <name> --json` and `gp start-refine-slices --epic <name> --json` that return structured `ContextBundle` JSON with architecture/slice paths, decisions, and learnings. The plan-slice orchestrator uses `start-plan` for initial context but doesn't use a start command for refinement (because `start-refine-plan` didn't exist at that time). These commands do exist now. Using them would keep the orchestrator consistent with the context assembly pattern and avoid hardcoding paths.
Resolution: DIRECTLY_ACTIONABLE

**[MINOR] Phase 2 explore-phase trade-off acknowledged but no path to improvement**
The plan includes a "Known trade-off" note about explore-phase losing parallel research capability (raised as I3 in round 1). The note says "parallel research can be added later if explore phases prove too slow." This is acceptable as a documented simplification, but the plan should note the specific mechanism for future improvement: the orchestrator could spawn multiple research agents in parallel (since the orchestrator can spawn agents), passing research topics from the explore-phase agent's return. This keeps the trade-off decision reversible without requiring changes to the flat agent hierarchy.
Resolution: DIRECTLY_ACTIONABLE

**[MINOR] `reviewers-language.md` source path resolved but extraction mechanism unspecified**
Round 1 flagged that `reviewers-language.md` doesn't exist in the repo. The plan now correctly references the installed plugin cache path (`~/.claude/plugins/cache/goodplan-marketplace/goodplan/1.0.3/skills/refine-plan/references/reviewers-language.md`). However, the task says "Source: extract and adapt from installed `skills/refine-plan/references/reviewers-language.md`" — it should specify that the implementer reads the installed file and extracts the TypeScript section into a new `skills/_shared/references/review-typescript.md` in the repo. The word "extract" is ambiguous — it could mean copying, adapting, or referencing. Since this is a one-time extraction into a repo-owned file (not an ongoing dependency on the installed cache), make the task explicit: "Read the installed file at `~/.claude/plugins/cache/.../reviewers-language.md`, extract the 'TypeScript and JavaScript Reviewer' section, adapt it for the agent-based pipeline format, and write to `skills/_shared/references/review-typescript.md`."
Resolution: DIRECTLY_ACTIONABLE

**[MINOR] Stagnation/reduction detection logic differs from plan-slice without justification**
Phase 4 step 7 says "If stagnation (scores plateau for 2 rounds) or round cap (default 3, configurable via `GP_CREATE_EPIC_MAX_ITERATIONS`)." The plan-slice orchestrator uses different thresholds: stagnation = 2 consecutive no-change rounds, reduction = 2 total reduction rounds (any position), hard cap = 10 (configurable via `GP_PLAN_SLICE_MAX_ITERATIONS`). The create-epic plan uses a default cap of 3 and doesn't specify the stagnation/reduction rules as precisely. The create-epic refinement loop should use the same exit condition logic as plan-slice (steps 4f-v items 1-5), just with a different env var name. The lower default cap (3 vs 10) makes sense for architecture/slices refinement (less iteration expected), but the detection logic should be consistent.
Resolution: DIRECTLY_ACTIONABLE
